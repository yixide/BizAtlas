Project Atlas

把复杂软件系统，变成可探索的业务地图。
Business-first · Code-backed · AI-maintained

面向 AI 辅助开发与多人协作时代的本地项目地图平台。将业务功能、配置依赖、数据流向、部署条件和代码证据连接起来；让负责人无需记住所有技术细节，也能按需进入系统，理解影响、接手工作、完成交接。

独立开源平台私有项目数据留在项目内业务优先，技术按需下钻Codex 等 AI 维护地图只读加载优先
产品定义稿 · v0.1 · 2026 年 10 月 30 日 · 用于交给本地开发 AI 作为需求依据
01

创始用户的真实痛点

本项目并非因为“没有文档”。恰恰相反：项目已有设计文档、功能清单、表结构、数据流转和 AI 工作规范，AI 通常能凭这些材料正确开发与排障。问题出现在人的系统认知跟不上 AI 与多人开发的变化速度。

PAIN / 01

开发速度远超认知带宽

需求和代码由多人及 AI 持续并行推进，负责人不再参与多数实现细节；系统并未必然失控，但个体已无法持续跟踪每个模块的演变。

PAIN / 02

“AI 能查到”不等于“人知道影响”

故障时把现象交给 AI，修复后由 AI 归档。下次仍要重新查；人不想也不需要记住全部表名、配置、函数和故障细节。

PAIN / 03

恢复服务不等于恢复业务能力

经历生产勒索软件事故后，系统重建时只确认服务能启动，遗漏部分运行时配置，导致后续两次配置相关故障。需要可核验的部署依赖，而非纯文字提醒。

PAIN / 04

现有代码关系图信息过载

普通图谱画满函数调用、节点和箭头，难以回答“这个业务是什么、依赖什么、改动会影响什么”。默认视角过低，无法产生业务认知。

PAIN / 05

大量功能并非本人开发

即使有时间阅读，也不可能掌握团队和 AI 完成的每项功能；更合理的方式是通过业务导航按需获得上下文。

PAIN / 06

难以低成本交接

项目能够被某个 AI 正确维护，不代表运维、其他开发者或另一个 AI 可以立即理解跨业务、配置、数据和运行依赖。

“我可以完全不参与技术细节，但需要项目能被 AI 和其他人可靠接手；需要时，我又能自由切回开发者角色。”
02

产品定位、目标与边界

Business-first

业务先于代码

首页以业务领域及业务功能组织信息。默认不展示函数、方法调用和低价值技术连线。

Code-backed

每个重要结论可追溯

业务链、配置和数据依赖都能定位到文件、符号、SQL 或设计文档；区分确认和推断。

AI-maintained

由项目内 AI 更新数据

Atlas 是展示与查询平台，不强制调用某家模型，也不把生成器内嵌为唯一入口。

一句话定义：Project Atlas 是一个读取私有项目结构化地图数据、提供业务级可视化探索与跨层影响分析的通用开源服务。
是不是
项目级业务导航与依赖认知平台强制展示所有函数调用的代码图谱
跨业务、配置、数据库、部署的关联层现有设计文档或知识库的替代品
独立开源软件 + 可移植数据规范绑定某个私有项目或某个 AI 供应商的工具
可追溯的影响分析与部署检查入口未经验证就能自动操作生产环境的控制器
本地优先、私有数据默认不上传默认采集项目代码和配置到云端的 SaaS
03

用户角色与核心使用场景

模式 01

业务用户

搜索功能、看到业务含义、依赖和影响，不要求理解具体代码。

  • 我要修改这项业务，影响谁？
  • 某功能到底属于哪个模块？
模式 02

负责人 / 运维

看跨模块依赖、配置风险、环境基线和恢复核对，不必自己管理技术细节。

  • 迁移文件目录还需改哪里？
  • 新环境恢复是否完整？
模式 03

开发者 / AI

逐层钻取到接口、表字段、SQL、配置、代码证据，用于开发、排障及交接。

  • 这张表被哪些功能写入？
  • 这个配置的上下游是什么？

角色切换不是权限切换。 同一个人可以按需从业务视角下钻到技术视角；实际写入项目文件、访问生产信息的权限仍需独立控制。

04

总体架构与私有数据边界

最重要的架构约束：Atlas 平台不持有某个业务项目的知识真相。真相保存在各自的私有项目中，由项目内的 AI 或专用工具维护。Atlas 只消费符合标准的数据。

Atlas 仓库（公开）

平台 UI、数据模型、验证器、通用图查询、图引擎适配层、示例虚构项目、公开文档。不得包含真实业务项目数据。

业务仓库（私有）

业务代码、原有文档、结构化地图、项目布局与证据。可按需把 Atlas 数据文件纳入原有 Git 管理，形成版本对应关系。

安全边界：即使只有“项目地图”，也可能泄露业务拓扑、数据库表、内部路径和配置项名称。私有地图不是无敏感信息的展示数据，默认绝不公开同步。
05

技术选型与复用策略

选型原则：优先利用成熟图引擎及架构可视化能力，自己只开发产品特有的“业务语义、交互、查询、证据和跨层影响分析”。

模块推荐方案理由与要求状态
前端平台React + TypeScript + Vite适合可组合工作台、图引擎集成、开源组件生态；若团队明确更擅长 Vue，可替换。建议
可视化主候选AntV G6 5.xCombo 嵌套分组、折叠、跨组合连线转接、布局、缩放、聚焦、自定义节点；MIT。优先 PoC
复用替代候选LikeC4DSL/模型驱动、多视图和逐层钻取、React 嵌入、模型构造 API；MIT。重点验证是否可承载产品交互。对比 PoC
底层代码图参考CodeBoarding已有静态分析 + AI 架构生成、analysis.json、本地分析能力；分析引擎 MIT。参考设计，不依赖其托管 UI。参考与选用评估
其他图引擎备选Cytoscape.js成熟图查询与网络分析；若复杂关系查询表现更重要可对比，核心 MIT。备选
数据格式JSON / JSONL + JSON Schema易于 AI 生成、Git Diff、验证和跨语言消费；避免绑定 G6 或 LikeC4 内部格式。确定方向
本地服务Node.js + 小型本地 HTTP API负责访问允许目录、校验数据、索引查询和静态网页；默认监听 127.0.0.1。建议
搜索与索引第一版内存索引 / 轻量缓存避免引入 Neo4j 和复杂后台。数据规模验证后再考虑 SQLite FTS 或图索引。MVP

G6 需要验证的能力

  • 业务 Combo 折叠及跨模块聚合线
  • 默认单模块聚焦 + 固定多模块展开
  • 可稳定恢复的布局坐标
  • 大图裁剪、按需装载与性能

LikeC4 需要验证的能力

  • 从 Atlas 标准数据生成多层模型和视图
  • 嵌入式单节点聚焦和多模块固定
  • 关系聚合、详情联动及自定义行为
  • 源证据、表/配置视角和布局保存
技术决策：先用同一份虚构项目数据完成 G6 和 LikeC4 的小型验证。若 LikeC4 无法以合理成本满足交互，就用 G6 构建专属 Viewer。无论结果如何，Atlas 数据契约保持引擎无关。

操作行为原则
搜索跨业务名、别名、表、配置、接口搜索；定位内部节点时先展开所属业务领域。搜索是主入口，不要求用户记住表名。
单击节点高亮节点、直接关系及重要路径；右侧显示业务解释和证据。不立即灌入全部细节。
展开业务模块默认同一时刻只聚焦一个展开模块，其他非固定模块自动折叠。默认控制复杂度。
固定模块手动固定其他模块，使其保持展开，支持跨模块对照。模式 C，已确定。
双击功能进入功能详情；显示业务规则、重要调用路径、读写表、配置及可选技术实现。逐层下钻。
单击聚合连线展示两个模块之间的关系类别和数量；按需打开明细。不要数十条平行箭头。
搜索配置或数据表以所选配置或表为中心，切换上下游影响视图和证据列表。所有类型节点可作为中心。
手动拖动与保存首次自动布局，调整后记住节点位置；增量更新尽量保持未变节点稳定。防止每次打开都是陌生地图。
视图分享与导出导出当前子图、依赖摘要及引用证据；导出前提示可能包含私有信息。满足交接，不默认公开。

要支持的不是单一严格树：功能可以归属于一个主业务领域，同时与多个领域关联；数据库表、共享组件、配置和外部服务则可被多个业务引用。归属关系和依赖关系必须分开建模。

连线呈现原则

首页聚合

仅显示业务领域之间的重要关系。一组底层关系汇总为一条可点击的聚合连线，附数量或关系类型。

类型可区分

调用、数据读写、事件、配置和部署依赖使用不同标识；可按类型过滤，不只依赖颜色。

证据可区分

已验证关系与待确认推断使用不同线型/标记；点击可查看来源，避免漂亮但不可靠的图。

07

详细功能需求清单

优先级：P0 = 第一版必须；P1 = 早期重要扩展；P2 = 后续演进。每项需求都应给出可验证的用户行为，不以“图能画出来”作为完成标准。

F-01
P0

私有项目加载与多项目切换

用户选择一个被允许的本地项目目录；Atlas 读取其地图清单、验证版本与文件完整性，加载后显示项目名称、分支、对应提交、生成时间和数据状态。

验收：切换项目不串数据；缺失、过期、无权限时可诊断，不显示虚假“完整”。
F-02
P0

业务分组首页

首页按业务领域聚合展示模块，仅保留有意义的跨领域依赖线；公共能力独立分组；主归属稳定，非树形依赖另行表达。

验收：默认画面不出现函数级调用；可通过领域快速找到功能。
F-03
P0

聚焦、展开、固定、多层下钻

单击聚焦，展开当前模块；默认其他未固定模块折叠。可固定多个模块做对照，进入功能层后再按需看服务、表、配置和源码。

验收：连续切换模块不乱；折叠后的跨模块连线语义保持正确。
F-04
P0

统一搜索与双向关系导航

通过业务名、别名、表名、配置、接口、类名检索。节点可作为关系中心，切换上游/下游、1~3 层及关系类型过滤。

验收：从业务找表，从表反查业务，从配置反查被影响功能。
F-05
P0

关系证据和可信度

重要关系包含类型、方向、来源、代码/文档引用、验证状态和版本；支持打开本地证据定位点（在许可范围内）。

验收：无法验证的依赖清楚标注为“文档声明/AI 推断/待确认”。
F-06
P0

配置与数据依赖视图

配置→读取代码→功能→运行条件；业务→数据读写→表/关键字段；支持聚合和局部明细。

验收：选定文件存储配置可列出影响路径与尚需核实的生产项。
F-07
P0

布局保存、版本标识和缺失状态

保存手动布局与固定展开状态；显示当前地图所对应提交和可能的过期状态；找不到证据时显示“未知”，不静默隐藏。

验收：重新载入后位置稳定；仓库提交变化但地图未更新时有明确提醒。
F-08
P1

变更影响分析

选择模块、字段或配置，沿不同类型关系追踪受影响业务，展示“直接影响 / 间接候选 / 待验证”及回归建议；避免将图遍历结果当作确定性影响。

验收：结果具有可点击证据和明确的推断边界。
F-09
P1

部署地图与恢复对照

展示服务、环境、端口、目录、证书、IIS/反向代理、DB、缓存、外部依赖；关联环境基线与实际验证记录，生成部署检查清单。

验收：服务启动成功但缺失关键业务配置时，不得显示“全部恢复”。
F-10
P1

Git 版本对照与地图增量变化

对比两次地图版本，识别新增、删除、变更的业务依赖；输出变化摘要，避免每次整图重新布局。

验收：能够说明某个跨业务依赖在哪个提交首次出现。
F-11
P1

交接与只读导出

导出局部子图、功能说明、关联配置/数据及证据引用的 HTML/Markdown/JSON；必要时脱敏。

验收：不拥有业务仓库开发经验的接手人可以沿地图找到可靠入口。
F-12
P2

AI 工具查询接口 / MCP

对标准数据提供 findFeature、getDependencies、findImpact、getDeploymentChecklist 等只读能力，供本地 Codex 等工具消费。

验收：不需要打开 Web 页面，AI 也能获得相同的关系和证据。
08

项目内结构化数据规范

建议在每个私有项目内提供 .project-atlas/。以下是候选格式，不是已经发布的正式 Schema。真正实施时先冻结最小字段与版本迁移规则，确保框架独立于具体 AI 和图引擎。

my-private-repo/
├── src/                           # 原业务代码
├── docs/                          # 原有设计与业务文档
└── .project-atlas/
    ├── manifest.json              # 项目、schemaVersion、commit、生成时间
    ├── entities.jsonl             # 业务、功能、服务、表、配置、任务等实体
    ├── relations.jsonl            # 有方向、有类型的依赖关系
    ├── evidence.jsonl             # 代码/SQL/文档证据引用
    ├── views.json                 # 首页分组、视图定义、默认过滤
    ├── layouts.json               # 可选的共享布局数据
    └── validation-report.json     # 扫描覆盖与待确认项
对象最低字段（草案）规则
Entityid, type, name, parentId?, description?, aliases?稳定 ID；display name 可改；归属不是全部依赖。
Relationid, source, target, type, evidenceIds[], status必须有方向；调用/读取/写入不能混为一种“关联”。
Evidenceid, kind, path, symbol?, lineStart?, lineEnd?, commit?相对仓库路径；标记是否经过验证；不要复制机密全文。
ManifestschemaVersion, projectId, sourceCommit, generatedAt, generator每次地图对应源版本；校验数据格式与兼容性。
Viewid, title, focusIds, filter, depth, groupBy同一图谱可以投影为业务图、数据图、配置图或部署图。
LayoutviewId, nodePositions, expandedIds, pinnedIds与语义关系分离；尽可能保留历史位置；允许个人覆写。

关系类型（第一版候选）

BELONGS_TO / 业务归属
CALLS / 调用
READS / 读取
WRITES / 写入
USES_CONFIG / 使用配置
PUBLISHES / 发布事件
SUBSCRIBES / 订阅事件
DEPENDS_ON / 依赖

最小数据示例（纯虚构）

// entities.jsonl（逐行 JSON）
{"id":"domain.assets","type":"domain","name":"文件资源"}
{"id":"feature.upload","type":"feature","name":"文件上传","parentId":"domain.assets"}
{"id":"config.fileRoot","type":"config","name":"FileStoragePath"}
{"id":"service.upload","type":"service","name":"UploadService"}

// relations.jsonl（逐行 JSON）
{"id":"rel.001","source":"feature.upload","target":"service.upload","type":"USES","status":"verified","evidenceIds":["ev.001"]}
{"id":"rel.002","source":"service.upload","target":"config.fileRoot","type":"USES_CONFIG","status":"verified","evidenceIds":["ev.002"]}

// evidence.jsonl（逐行 JSON）

09

AI 如何生成、维护和消费地图

平台不内置某个模型，也不把“AI 自己说已更新”当成更新保障。由项目仓库中的工具与 AI 工作规范共同维护，Atlas 通过 Schema 校验、证据检验与版本状态展示结果。

首次扫描与复用已有文档

先读取现有项目规范、功能列表、表结构和设计资料，再结合代码、SQL、配置提取关系；避免重复编写文字知识库。

产生结构化地图变更

增量添加或更新实体、关系、证据、视图；保留稳定 ID 与来源提交；人工确认的业务归属不得随意重分组。

运行可执行校验

检查 Schema、引用完整性、关系方向、循环归属、源文件和关键符号存在性；无法确认的记为 unknown/claimed/inferred。

发布与展示

Atlas 重新读取数据，保留用户布局，计算影响视图；当工作树变化而地图尚未同步时提示版本差异。

开发、部署与故障复用

本地 AI 在任务前查询相关关系；执行后更新关系与验证证据。部署验证结果写入项目可管理的检查记录，而不是修改生产环境的真实状态推测。

项目 AI 的责任

  • 理解代码及业务语义，维护结构化关系
  • 标注来源和不确定性
  • 修改代码后识别地图影响
  • 保持现有架构规范与业务归属

Atlas 的责任

  • 加载和验证标准数据
  • 显示图谱、搜索、筛选与上下游
  • 提供关系查询与影响候选
  • 提示数据过期、缺失或不一致
10

安全、隐私与运行约束

本地优先

默认监听 127.0.0.1，不开放公网，不主动上传代码、配置或关系图。需要 LAN/远程访问时必须显式启用认证和授权。

目录白名单与只读默认

只访问明确选择/授权的项目目录；防止路径穿越和符号链接逃逸。Atlas 默认不写业务仓库，保存共享布局需要用户授权。

秘密信息不入图

允许记录“存在数据库凭据配置项”，不允许存储凭据值、令牌、私钥、生产连接串中的敏感部分；导出需脱敏提醒。

可信证据与生产边界

本地代码无法证明线上 IIS、文件权限或数据库实际配置。生产状态必须通过授权采集与验证，且查看地图不等于拥有生产操作权。

关于勒索软件事故对应的产品要求：地图要帮助识别恢复前置条件和配置遗漏，但不能被宣传成防勒索软件或安全取证工具。备份不可变性、离线副本、恢复演练、入侵溯源应由独立安全流程负责。
11

MVP 范围与刻意不做的事

MVP / P0

先做一条完整可用的体验链

  • 打开 Atlas → 加载一个私有项目
  • 首页业务领域全景 + 搜索
  • 聚焦、展开、固定其他模块
  • 功能 → 服务/表/配置 → 证据
  • 表或配置的反向依赖查询
  • 关系聚合、可信状态展示
  • 稳定布局、版本状态、数据校验
  • 虚构示例项目 + 私有项目接入示例
不在 MVP 内

避免大而全

  • 重写多语言 AST 扫描器
  • 自建通用数据库图引擎
  • 强制搭建 Neo4j 或 K8s
  • 默认扫描本机所有仓库
  • 生产自动部署、自动修复和远程控制
  • 实时监控大屏、日志平台、APM
  • 从函数图自动“猜对”全部业务语义
  • 由平台托管私有项目数据到云端
MVP 产品价值检验：负责人能否不看源码，就从一个业务入口找到关联表、配置、部署要求；需要时继续下钻并看到可信证据。

必须通过的真实场景验收

场景操作可接受结果
业务找数据搜索一个核心业务功能进入业务模块，找到主要写入/读取的数据表及其证据，默认不展示全部函数。
数据反查业务搜索某张跨功能共享表列出直接读写者、对应功能与关系方向，能打开来源。
静态资源迁移搜索文件存储配置并执行影响分析展示文件写入/读取、历史路径、IIS/映射、权限、配置与数据库候选；未从本地证实的标记待验证。
部署恢复打开某服务部署视图列出必需配置、服务与资源；区分代码要求、环境基线和已现场验证，不以“启动成功”替代验收。
多人开发变化修改一个模块依赖后增量更新地图新关系出现，相关视图更新，其他模块布局基本保持，来源提交可追溯。
交互与性能模拟几十个领域、数百个功能和数千条关系首页按领域聚合仍易读；需要实际基准测试，不凭空承诺固定帧率或加载耗时。
隐私隔离导入两个项目并尝试访问未授权目录数据严格隔离；未授权路径不可读取，导出可提示脱敏。
交接由不熟悉项目的人使用地图定位故障入口无需了解原代码目录，也能找到业务、配置和代码证据；未知部分明确说明。

建议实施路线

阶段 0 · 先验证图引擎，不先开发平台

准备同一份虚构业务 JSON：4 个业务领域、15 个功能、10 个数据表、8 个配置与若干依赖；分别做 G6 与 LikeC4 PoC，验证聚合、钻取、多固定展开、布局和详情联动。

阶段 1 · 冻结 Atlas 最小数据协议

明确实体、关系、证据、视图和版本；创建 JSON Schema、校验器、示例数据。图引擎只消费转换后的视图模型，不能直接成为存储格式。

阶段 2 · 交付最小 Web Viewer

实现本地项目选择、首页业务分组、搜索、聚焦固定、分层下钻、关系明细、证据追踪、状态提示和布局保存。

阶段 3 · 用真实私有项目验证

由项目内 Codex 根据现有文档和代码生成结构化地图，先覆盖少量核心业务；验证配置与数据库双向导航，改进数据模型。

阶段 4 · 可持续维护与开源发布

接入增量更新与一致性检查、提供示例与使用教程、检查许可证和敏感数据；对外发布仅包含平台和虚构数据。

开发 AI 执行原则：按阶段交付可以运行和验证的产物，不用大段静态页面假装拥有图引擎功能；不得在实现 Atlas 的过程中擅自修改真实业务项目源代码、生产配置和数据库。
